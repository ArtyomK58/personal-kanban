# Канбан — личная доска всех проектов с MCP

Небольшая self-hosted канбан-доска для одного владельца. Все проекты на одной доске; проект — это цветной тег.
Агенты (Claude Code, Codex и др.) работают с той же базой через встроенный **MCP-сервер**.

- Доска: 4 колонки («Входящие», «В работе», «На проверке», «Готово»). Карточки перетаскиваются между колонками и внутри колонки, порядок сохраняется. Есть быстрое создание задачи прямо в колонке.
- Фильтр по проектным тегам: можно выбрать один тег или несколько. При нескольких тегах показываются задачи, у которых есть **любой** из выбранных. Активный фильтр выводится явной строкой «Показаны задачи: A или B · 7 из 15 · Сбросить». Фильтр хранится в URL и запоминается между визитами. Поиск идёт по названию, описанию и комментариям.
- Клик по карточке открывает задачу **справа в панели**, доска с фильтром и прокруткой остаётся на месте (`/?task=42`). Кнопка «Открыть страницей» ведёт на постоянный адрес `/t/42`. Ссылку также можно скопировать прямо с карточки. «Назад», Esc и ✕ закрывают панель. Перезагрузка страницы панель сохраняет.
- В задаче: Markdown-описание, комментарии с автором и временем (комментарии агентов помечены «агент»), теги, статус и срок.
- **Приоритет задачи**: ровно три значения — «Низкий», «Обычный» (по умолчанию), «Высокий» (`priority = low | normal | high`). Меняется переключателем «Приоритет» в панели и на странице задачи, сохраняется сразу. На карточке высокий отмечен «⌃ Высокий», низкий — «⌄ Низкий» (с подсказкой), обычный не отмечается; у эпика в шапке карточки — только значок с подсказкой. В каждой колонке карточки автоматически сгруппированы по приоритету: высокий → обычный → низкий. Перетаскивание сохраняет ручной порядок внутри одного приоритета; перенос между колонками сохраняет приоритет. У эпика и его задач приоритет независимый.
- **Замороженные задачи** отмечаются снежинкой и идут внизу своей колонки. Заморозка сохраняет статус и приоритет.
- **Автоматическое завершение.** После календарного месяца подряд в «Готово» обычная задача переходит в скрытый статус «Готово окончательно» (`done_final`). Её можно открыть по прямой ссылке или найти через MCP и вернуть в одну из колонок. Эпики сохраняют ручной статус.
- **Эпики.** Эпик — карточка особого вида на той же доске и в тех же колонках, со своим ручным статусом; он объединяет обычные задачи. У задачи не больше одного эпика, эпики не вкладываются друг в друга, проект по-прежнему тег (эпик ≠ тег).
  - Карточка эпика: компактная карточка с меткой «◆ ЭПИК», тегами проекта и оттенком, общим с её задачами. Статус эпика сам не меняется.
  - Задача эпика — та же карточка плюс строка «◇ Имя эпика» над названием; клик по ней открывает эпик и не запускает перетаскивание.
  - Панель/страница эпика: прогресс, описание, комментарии, список «Задачи эпика» со статусами, «+ Новая задача в эпике» и «Привязать существующую…».
  - Панель задачи: строка «Эпик» со ссылкой на родителя и «Изменить» — поиск, эпики своего проекта первыми, «Без эпика», «+ Создать эпик…». Привязка не меняет теги и тексты задачи.
  - Создать эпик можно из быстрого добавления в колонке (переключатель «Эпик»), из выбора эпика, из фильтра эпика и кнопкой «Сделать эпиком» в задаче без эпика.
  - Отдельный фильтр «◇ Эпик: все ▾» справа от тегов: показывает эпик и его задачи (`/?epic=51`), сочетается с тегами и поиском, сохраняется в URL и при перезагрузке, сбрасывается ×.
- Черновики описания и комментария хранятся локально в браузере. Они не теряются, если закрыть панель, перезагрузить страницу или перейти на другую.
- Вход по токену: отдельный экран; вход запоминается без серверного срока; выход и постоянная защита от перебора (см. ниже).
- **Два независимых поля задачи**:
  - `human_description` — описание, которое видит владелец в UI;
  - `agent_notes` — заметки агентов. Они хранятся отдельно и доступны только через аутентифицированный MCP. Их нет ни в одном ответе UI API, нет в DOM и они не попадают в поиск UI. Правка одного поля никогда не меняет другое.

  Это скрытие от обычного интерфейса, а не защита от владельца сервера: у кого есть файл БД, тот видит всё.

Развёртывание на VPS за HTTPS-прокси описано в [deploy/DEPLOY.md](deploy/DEPLOY.md).

## Быстрый старт (Docker Compose)

```bash
docker compose up -d --build              # порт 8080 только на 127.0.0.1
docker compose exec kanban cat /data/bootstrap-token.txt
```

1. Откройте http://127.0.0.1:8080, вставьте токен и войдите.
2. Сохраните токен в менеджере паролей.
3. Удалите файл: `docker compose exec kanban rm /data/bootstrap-token.txt`.

При первом запуске сервер сам создаёт токен владельца и пишет его в `/data/bootstrap-token.txt` (права 0600). В лог токен не попадает. В БД хранится только SHA-256 хэш.

Если нужны демо-данные (синтетические проекты и задачи, только на пустой доске):

```bash
docker compose exec kanban node dist/server/cli.js seed-demo
```

Настройки — переменные окружения (см. `.env.example`): `KANBAN_BIND`, `KANBAN_PORT`, `COOKIE_SECURE`, `TRUST_PROXY`.
Открывать доступ снаружи стоит только через ваш HTTPS reverse proxy. В этом случае задайте `COOKIE_SECURE=1` и `TRUST_PROXY` — список адресов прокси (например `loopback` для прокси на том же хосте без Docker-сети); значение `1` означает только loopback.

## Вход и токены

**Вход запоминается.** Токен вводится один раз. Сервер выдаёт случайный идентификатор сессии (256 бит) в cookie `pk_session` с флагами `HttpOnly; SameSite=Strict` и `Secure` при `COOKIE_SECURE=1`; в БД хранится только его SHA-256.

- На сервере сессия **не истекает по времени**: она живёт, пока вы не нажмёте «Выйти», не отзовёте токен или браузер не удалит cookie.
- Браузеры ограничивают срок постоянной cookie (в настройках доски используется срок 400 дней). Поэтому cookie выдаётся на 400 дней и перевыпускается при активности (не чаще раза в сутки): пока вы хоть иногда открываете доску, повторно входить не придётся.
- Вход переживает перезапуск браузера, контейнера и обновление версии. Сессии, созданные до обновления, тоже остаются действительными.
- «Выйти» удаляет сессию на сервере. `token revoke` отзывает токен и все его сессии.
- Сам токен в браузере не хранится: его нет ни в localStorage, ни в URL.

Каждому агенту лучше выдать свой токен: имя токена становится автором его комментариев.

```bash
docker compose exec kanban node dist/server/cli.js token create claude       # агентский токен, печатается один раз
docker compose exec kanban node dist/server/cli.js token create laptop --owner
docker compose exec kanban node dist/server/cli.js token list
docker compose exec kanban node dist/server/cli.js token revoke 3            # отзывает токен и его сессии
docker compose exec kanban node dist/server/cli.js sessions list
```

Токены — `pk_` + 32 случайных байта (256 бит, `crypto.randomBytes`). В БД хранится SHA-256, поиск идёт по хэшу. Токен передаётся только в теле запроса на вход или в `Authorization: Bearer …`, никогда в URL. Cookie-мутации требуют заголовок `X-Kanban-Client` (защита от CSRF). MCP принимает только Bearer, cookie браузера на `/mcp` не действует.

### Защита от перебора

Лимитер один для всех мест, где проверяется секрет: формы входа, Bearer на `/api/*` и Bearer на `/mcp`. Сменой эндпоинта его не обойти. Состояние хранится в SQLite, поэтому рестарт блокировку не снимает. Проверка идёт на сервере до поиска токена; заблокированный клиент получает `HTTP 429` с `Retry-After`. Проверка, поиск токена и учёт неудачи выполняются атомарно, параллельные запросы лимит не превышают.

| Правило | Значение |
|---|---|
| Неудачных попыток с одного адреса (IPv6 — по /64) | 5 за 15 минут |
| Блокировка адреса, прогрессивная | 5 мин → 15 мин → 60 мин (дальше по 60 мин) |
| Сброс истории блокировок | после 24 ч без неудачных попыток |
| Общий бюджет со всех адресов | 50 неудач за 15 минут → глобальная блокировка на 15 мин |
| Кто проходит при глобальной блокировке | адреса, с которых за последние 90 дней был успешный вход или Bearer-запрос |

- Успешные запросы бюджет не расходуют. Успех обнуляет счётчик только своего адреса и никогда не снимает чужие блокировки.
- Пока адрес заблокирован, отклоняется даже правильный токен с этого адреса. Иначе блокировка ничего бы не ограничивала.
- Уже вошедший браузер блокировки не замечает: проверка cookie-сессии лимитер не трогает.
- Неизвестная или устаревшая cookie просто удаляется. Подобрать её нереально: 256 бит.
- Адрес клиента берётся только от доверенного прокси (`TRUST_PROXY`, на VPS — Caddy на этом же хосте). Caddy перезаписывает `X-Forwarded-For` реальным адресом, поэтому подделка `X-Forwarded-For` или `X-Real-IP` не помогает.
- Аварийно снять все блокировки: `node dist/server/cli.js limits reset`.

Абсолютной неуязвимости это не обещает. Но с токеном в 256 бит и не более ~120 попыток в сутки с одного адреса (≈4800 в сутки со всех адресов) подбор практически невозможен.

## MCP

- Транспорт **Streamable HTTP**, без сессий: `POST http://<host>:8080/mcp`, заголовок `Authorization: Bearer <token>`.
- Дополнительно есть **stdio-адаптер** внутри контейнера: `docker compose exec -T kanban node dist/server/mcp-stdio.js`.

Инструменты (19): `list_tasks` (теги any/all, статус, полнотекстовый поиск, `priority` (одно значение или массив), `kind`, `epic_id` = номер или `"none"`, `include_epic`), `get_task` (оба поля явно разделены: `human_description` и `agent_view.agent_notes`; у эпика — `progress` и `children`), `create_task` (`kind: "epic"` создаёт эпик, `epic_id` кладёт новую задачу в эпик, `priority`, по умолчанию `normal`), `update_task` (также `priority`, `kind` и `epic_id`, `null` — убрать из эпика; не переданные поля не меняются), `update_human_description` (replace/append), `get_agent_notes`, `set_agent_notes`, `append_agent_notes`, `move_task` (статус + before_id/after_id/index), `list_comments`, `add_comment`, `list_tags`, `create_tag`, `assign_tags`, `unassign_tags`, `list_statuses`, **`list_epics`** (эпики с прогрессом и приоритетом; фильтры status/priority/tags/query), **`get_epic`** (эпик, его задачи и прогресс), **`set_task_epic`** (привязать/перенести/отвязать задачу). Все задачи в ответах несут `priority`, `kind`, `epic_id`, `epic {id,title}` и для эпиков `progress {done,total}`. Прежние вызовы работают без изменений. Полные схемы — в [docs/MCP-TOOLS.md](docs/MCP-TOOLS.md).

Ошибки возвращаются как `isError: true` с кодом: `not_found: Задача #99 не найдена`, `conflict: …`, `invalid: …`. Ошибки эпиков: `epic_self`, `epic_nested` (эпик в эпике или эпиком становится задача с эпиком), `epic_parent_missing`, `epic_parent_not_epic`, `epic_has_children` (эпик с задачами нельзя сделать обычной задачей), `not_epic` (get_epic для обычной задачи).

Подключение (примеры без секретов — в [examples/mcp/](examples/mcp/)):

```bash
# Claude Code
export KANBAN_TOKEN=pk_...          # агентский токен
claude mcp add --transport http kanban http://127.0.0.1:8080/mcp --header "Authorization: Bearer $KANBAN_TOKEN"
```

Codex — [пример нативного подключения](examples/mcp/codex-config.toml). Клиенты без поддержки заголовков — через `mcp-remote` (`examples/mcp/mcp-remote.mcp.json`).

**Доступ к серверу через SSH.** Порт закрыт снаружи, поэтому проще всего пробросить его через SSH:

```bash
ssh -N -L 8080:127.0.0.1:8080 your-server
```

После этого используйте `http://127.0.0.1:8080/mcp`. Второй вариант — stdio поверх SSH (`examples/mcp/stdio-over-ssh.mcp.json`).

Изменения из MCP и UI видны сразу в обе стороны:
- UI получает сигнал об изменении по SSE (`/api/events`) и перечитывает данные;
- изменения через stdio-адаптер (другой процесс) UI подхватывает при фокусе окна или раз в минуту.

Проверка живого инстанса настоящим MCP-клиентом:

```bash
KANBAN_URL=http://127.0.0.1:8080 KANBAN_TOKEN=pk_... node scripts/mcp-smoke.mjs
```

## Резервная копия и восстановление

Данные — один файл SQLite (`/data/kanban.db`, режим WAL) в volume `kanban-data`.

```bash
scripts/backup.sh ./backups          # онлайн-копия через SQLite backup API, сервер не останавливается
scripts/restore.sh ./backups/kanban-example.db   # останавливает сервис, заменяет БД, запускает
```

Если `docker compose` у вас вызывается иначе, задайте `COMPOSE="docker-compose"`. Копии содержат токены (хэши) и agent_notes, храните их приватно.

## Разработка

```bash
npm ci
npm run dev:server        # API + MCP на :8080 (DATA_DIR=./data)
npm run dev:web           # Vite на :5173 с прокси на :8080
npm run typecheck && npm test
npm run build && npm start
```

Стек: Node 22, TypeScript, Express 5, better-sqlite3 (WAL, FTS5, миграции через `PRAGMA user_version`), `@modelcontextprotocol/sdk`, React 19, Vite, dnd-kit, react-markdown + remark-gfm (сырой HTML не рендерится). Внешних платных сервисов и LLM-провайдеров нет.

Тесты:
- `tests/server.test.ts` — auth, ограничение перебора, CSRF, независимость полей, теги, фильтры, порядок, рестарт, настоящий MCP-клиент;
- `scripts/ui-check.cjs` — сценарии UI в headless Chromium с промежуточными кадрами.

# Checkpoint карточки и ссылки на Kaeru

Цель: любой следующий агент открывает задачу, понимает сделанное и читает точную память о ней, сохраняя разделение контуров.

## Восстановление и запись

1. Получи карточку вместе с `agent_notes` (`get_task` или `get_agent_notes`). Найди последние checkpoint и ссылки на Kaeru; проверь указанные записи через `read`. Идентифицируй проект по задаче/тегам/контексту, не по CWD или имени модели.
2. Выбери настроенный MCP-сервер, контур и облако с доступом к памяти этого проекта. Для корпоративных и личных данных используй их соответствующие контуры. Имя инициативы бери из существующей памяти; тег доски не создаёт автоматически одноимённую инициативу.
3. Если ссылки пока нет, прочитай `initiatives → context(initiative) → search(initiatives, text, prefix) → read` в правильном контуре; ищи также по постоянному URL задачи. Вход в нужное облако — `cloud_recall`/pull с явным `cloud`, если поддерживается. Сначала переиспользуй подходящий существующий узел, чтобы не плодить дубликаты.
4. Сохрани существенный контекст, решение, план, результат или изменение состояния в Kaeru (`note`/`task`, обновление — `revise`/`replace`; точные источники — `reference`). В теле/свойствах укажи URL карточки, чтобы связь восстанавливалась в обе стороны. Не создавай копию всего описания ради отметки: достаточно полезного изменения и связи с задачей. Для уже существующей записи используй её ID, не создавай новую на каждый вызов инструмента.
5. После подтверждения сохранения добавь `append_agent_notes`: что изменено, что проверено, текущее состояние/блокер, следующий шаг и ссылки на Kaeru. При простой смене статуса запиши переход и его основание с указателем на актуальное состояние в памяти. Не пиши внутренний журнал в видимое описание или комментарии.
6. При смене статуса синхронизируй фактическое состояние доски и памяти в одном checkpoint. Отдельно обязательно оставь видимый комментарий с исходным и новым статусом и понятной человеку причиной по [правилу смены статуса в SKILL.md](../SKILL.md). Ссылки на Kaeru и служебные подробности остаются в `agent_notes`; checkpoint не заменяет комментарий. Сбой памяти не должен задерживать комментарий о подтверждённом переходе. «Готово» означает реально выполненную работу. При завершении/передаче укажи итог и где лежит контекст для продолжения.

Пиши один содержательный checkpoint на смысловой этап, а не на каждое чтение/команду. Не теряй существующие записи других агентов: по умолчанию добавляй, не заменяй целиком. После неопределённого результата сначала перечитай обе стороны, не дублируй записи и append вслепую.

## Точная ссылка на запись

Для каждого относящегося к задаче узла сохрани:

- `scope` и `cloud` (либо явно `local_only`, если облачной записи нет);
- `initiative`;
- `node_id` из реального ответа Kaeru и `name`, возвращённое сервисом;
- при необходимости `revision`, назначение записи и фактический инструмент/маршрут.

Если сервис вернул настоящий URL/URI записи, добавь Markdown-ссылку. Не выдумывай обработчик `kaeru://`, веб-адрес или ID: если URL нет, точной машинной ссылкой служит объект со scope/initiative/node_id, который можно открыть через `read`. Приведи рядом параметры чтения: `read({"initiative":"…","node":{"id":"…"}})` на указанном сервере. Одного общего имени инициативы вместо ссылки на узел недостаточно.

Форма записи (значения заполняются только из проверенных ответов):

```text
Checkpoint: <время и исполнитель>
Сделано / изменение статуса: …
Проверено: …
Следующий шаг / блокер: …
Kaeru:
- scope: …; cloud: …; initiative: …
  node_id: …; name: …; revision: …
  Назначение: актуальное состояние / решение / результат / источник
  Прочитать: read({"initiative":"…","node":{"id":"…"}}) через …
Публикация: подтверждена облаком / local_only / sync_pending
```

Для корпоративной задачи на этой доске достаточно разрешённого краткого результата и такого указателя. Не вставляй корпоративные документы, приватные логи, исходные данные или секреты в `agent_notes`; они остаются в корпоративной памяти.

## Недоступность и квитанции

- `state: partial` с созданным ID означает, что запись уже сохранена частично/локально: сохрани этот ID и не повторяй создание. Проверь `issues`, квитанцию публикации и текущий узел.
- Очередь/`publication`/`sync_pending` не равны подтверждённой облачной записи. Локальную ссылку обозначь именно как локальную.
- Если Kaeru недоступна, продолжай разрешённую работу с карточкой: кратко зафиксируй результат, `memory_unavailable`/`sync_pending`, правильный контур и то, что ещё нужно сохранить. Не придумывай ID и не подменяй корпоративную память личной. Следующий агент сначала дополняет недостающий указатель.
- Если Kaeru сохранена, а append на доске не подтверждён, не переписывай память: перечитай `agent_notes`, затем добавь только отсутствующий checkpoint с тем же ID.
